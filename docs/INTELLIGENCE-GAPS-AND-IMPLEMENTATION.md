# Intelligence Gaps and Implementation Plan

This document describes the remaining work required to fully implement the MineralView Intelligence Platform.

The Phase 1 repository provides the frontend architecture, interaction model, and data contracts needed to support the platform.

However, several critical capabilities described in the Intelligence Platform specification must still be implemented in backend services and platform infrastructure.

This document identifies those gaps and outlines the intended implementation approach.

The goal is to ensure that the system evolves into a **deterministic, auditable intelligence platform** rather than a generic AI interface.

---

# Current State

The current repository includes the following capabilities.

Frontend system architecture  
Owner Intelligence interface  
Explore data environment  
Advanced View analytics surface  
Continuous Intelligence interaction model  
Persona-aware routing  
Centralized frontend data service  
Backend integration documentation  
Data contracts and entity model  
Product surface architecture

These components define the user experience and frontend system structure.

However, several backend trust-layer systems remain unimplemented.

---

# Intelligence Platform Requirements

The Intelligence Platform architecture requires the following core capabilities:

Deterministic retrieval enforcement  
Tenant scoping and isolation  
Validation and fail-closed blocking  
Structured logging and replay  
Cost governance and rate limiting  
Evaluation harness for intelligence outputs  
Release gates and deployment discipline

These capabilities form the **trust layer** of the system.

Without them, the platform risks behaving like an unconstrained AI interface rather than a deterministic intelligence system.

---

# Gap 1: Deterministic Retrieval Enforcement

## Current State

The frontend architecture assumes deterministic datasets but currently retrieves mock data through the centralized service adapter.

There is no enforcement layer ensuring that intelligence outputs originate only from deterministic data queries.

## Required Capability

The system must enforce that:

- all intelligence responses originate from deterministic dataset queries
- all evidence references specific dataset objects
- no primary facts are generated by the AI model

## Implementation Approach

Introduce a **retrieval orchestrator service** responsible for:

1. parsing user intent
2. generating deterministic dataset queries
3. executing queries against backend data services
4. returning structured evidence objects

Example flow:

User question  
↓  
Intent parser  
↓  
Deterministic retrieval plan  
↓  
Data service queries  
↓  
Structured evidence objects  
↓  
Intelligence interpretation layer

The intelligence layer must never access raw databases directly.

All access must occur through controlled retrieval services.

---

# Gap 2: Tenant Scoping and Isolation

## Current State

The frontend includes persona-aware routing but does not enforce tenant-level data isolation.

True tenant isolation must occur in backend services.

## Required Capability

All queries must enforce user scope.

Examples:

- users can only access minerals associated with their accounts
- search queries must filter by allowed datasets
- cached responses must include tenant-aware keys

## Implementation Approach

Backend APIs should enforce:

Row-level security rules  
Authenticated query filtering  
Tenant-aware caching keys  
Explicit authorization checks on every endpoint

Example rule:


user_id == mineral_owner_id


Unauthorized access attempts must return errors rather than partial responses.

---

# Gap 3: Validation and Fail-Closed Behavior

## Current State

The Phase 1 frontend displays intelligence insights but does not enforce strict validation of those insights.

## Required Capability

Every intelligence response must pass validation checks before reaching the user.

Validation should include:

schema validation  
evidence presence  
numeric verification  
citation verification

If validation fails, the system must block the response.

## Implementation Approach

Introduce an **Intelligence Validator** that runs after the interpretation layer.

Validation checks should include:

required response fields  
valid evidence references  
correct numeric calculations  
permitted explanation categories

Example:


if evidence.length == 0
reject response


Failing responses should trigger fallback messaging rather than presenting uncertain outputs.

---

# Gap 4: Structured Logging and Replay

## Current State

The current repository does not include structured intelligence request logging.

## Required Capability

Every intelligence request should produce an audit log entry.

The log should include:

user ID  
tenant ID  
user query  
retrieval plan  
dataset identifiers used  
prompt version  
model version  
validation result  
timestamp

## Implementation Approach

Create a centralized logging service that records each intelligence interaction.

Logs should support:

debugging  
replay testing  
regression analysis

Replay capability should allow engineers to re-run previous requests against updated models or retrieval logic.

---

# Gap 5: Cost Governance

## Current State

The system currently does not enforce usage limits or cost controls for intelligence processing.

## Required Capability

The platform must control compute and model usage to prevent runaway costs.

Controls may include:

rate limiting  
daily usage quotas  
model routing rules  
request batching

## Implementation Approach

Introduce a **cost governance layer** that:

limits requests per user  
routes simple tasks to cheaper models  
blocks excessive request frequency

Example:


if requests_per_minute > threshold
reject request


Cost governance policies should be configurable.

---

# Gap 6: Evaluation Harness

## Current State

The repository includes testing capabilities but no structured intelligence evaluation harness.

## Required Capability

The system must include a regression test suite that evaluates intelligence outputs against known scenarios.

Example scenarios:

production decline explanation  
nearby drilling interpretation  
operator activity summary  
document parsing output

## Implementation Approach

Create a **golden test dataset** containing:

user query  
expected evidence  
expected explanation characteristics

Evaluation tests should verify:

correct evidence references  
correct numeric calculations  
acceptable explanation format

This harness should run during development and before production releases.

---

# Gap 7: Release Gates

## Current State

The repository currently lacks formal release controls for intelligence features.

## Required Capability

Intelligence updates should pass through controlled release gates.

Example gates:

schema validation tests  
evaluation harness tests  
security review  
manual verification

## Implementation Approach

Deployment pipelines should include:

automated test execution  
evaluation harness checks  
manual approval steps before release

Only validated intelligence changes should reach production.

---

# Implementation Priority

The recommended order for implementing the trust layer is:

1. deterministic retrieval enforcement  
2. tenant scoping and isolation  
3. response validation and fail-closed behavior  
4. structured logging and replay  
5. evaluation harness  
6. cost governance  
7. release gates

This sequence ensures that core trust guarantees are implemented before optimization or scaling.

---

# Relationship to Phase 1 Frontend

The Phase 1 frontend repository already provides the user experience architecture required for the Intelligence Platform.

The remaining work primarily involves backend services and platform infrastructure.

Once these backend capabilities are implemented, the frontend architecture can support a fully deterministic intelligence system.

# Summary

The MineralView Phase 1 repository provides the foundation for the Intelligence Platform user experience.

However, the full Intelligence Platform vision requires additional backend trust-layer systems.

These systems ensure that the platform remains:

deterministic  
auditable  
secure  
cost-controlled  
and trustworthy for mineral owners.

This document provides the roadmap for implementing those capabilities.
